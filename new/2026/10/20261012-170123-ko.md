## 1. AutoIndexer — 왼쪽에서 오른쪽으로 쓰되, 이미 쓴 문장으로 돌아가 고친다

- 원 제목: *AutoIndexer: Flexible-Order Decoding by Training Causal Models on Chains of Edits*
- 저자: Shu Ishida 외 5명, Autodesk Research
- 공개: arXiv v1, 2026-10-08 17:59:52 UTC
- 정규 URL: https://arxiv.org/abs/2610.12545
- 코드: https://github.com/AutodeskAILab/autoindexer (Apache-2.0)

일반적인 자기회귀 언어모델은 이미 생성한 토큰을 고칠 수 없다. AutoIndexer는 생성 순서와 최종 표시 순서를 분리하고, 모델이 `[EDIT]`와 `[RETURN]` 표식 및 두 개의 커서 위치를 예측하게 한다. 같은 연산으로 삽입, 삭제, 치환을 표현하며, 삭제된 토큰은 KV cache에서 물리적으로 지우지 않고 이후 attention에서 가린다. 이 때문에 최종 문서 순서는 앞뒤로 이동할 수 있지만 생성 과정은 여전히 자기회귀적이고 exact KV caching과 EOS 종료를 유지한다.

### 방법

깨끗한 문장에 무작위 역편집을 적용해 오류가 섞인 초안을 만들고, 모델은 그 역편집을 되돌리는 Chain of Edits를 학습한다. 실제 사람의 수정 이력이 없어도 일반 텍스트에서 자기지도 데이터를 만들 수 있다. 기본 Transformer 위에 4종 표식을 고르는 marker head와 편집 시작·끝 위치를 고르는 pointer 형태의 cursor head를 추가한다. 편집마다 화면상 토큰 위치가 바뀌므로, 저자들은 Chain-of-Edits RoPE와 fused attention kernel을 사용해 위치를 다시 배정한다.

보고된 8B 모델은 Qwen3 8B를 LoRA로 이어 학습했다. 비교용 Qwen3 LoRA와 AutoIndexer는 각각 10만 개 CPT 샘플, 약 2억 토큰을 사용했으며 8×NVIDIA H100 80GB, DeepSpeed ZeRO-2 환경에서 약 12,500 step을 학습했다. 데이터 혼합은 웹·교육·수학·코드이며 코드 비중은 약 25%다. 학습 예제 절반에 편집 교란을 적용했고, 합성 시퀀스는 평균 50회 편집을 포함했다.

### 실험 근거

| 조건 | AutoIndexer | 비교·해석 |
| --- | ---: | --- |
| MMLU 5-shot | 76.9 | matched Qwen3 LoRA 77.0 |
| MATH500 4-shot | 55.0 | matched Qwen3 LoRA 56.4 |
| HumanEval 0-shot, 별도 instruction 없음 | 59.2 | Qwen3 LoRA 51.2; diffusion baselines 10.4/0.6 |
| 자유 생성 삭제 오류 100개 | 정확 복구 53, 순개선 +66 | 편집 위치까지 모델이 결정 |
| 자유 생성 치환 오류 100개 | 정확 복구 18, 순개선 +31 | 정확 복구율은 아직 낮음 |
| 자유 생성 삽입 오류 100개 | 정확 복구 10, 순개선 +11 | 57개에서는 편집 자체를 시작하지 않음 |
| 깨끗한 초안 100개 | 89개 무수정 | 11개는 불필요한 편집 |

표준 벤치마크에서 matched 자기회귀 LoRA와 대체로 비슷하다는 결과는 “편집 기능을 넣어도 기본 능력이 완전히 무너지지는 않는다”는 근거다. 그러나 편집 진단은 유형당 100개, 단일 corruption, 64-token rollout 조건이다. HumanEval의 특정 설정 한 칸을 일반적인 코드 성능 우위로 확대하면 안 된다.

### 한계와 코드 상태

평가가 Qwen3 계열 8B 한 축과 저자 설계 진단에 집중되어 있고, 실제 장문 문서·여러 오류가 얽힌 코드베이스·대화형 편집의 지연시간은 제시하지 않는다. 여러 편집은 순차적이므로 최종 latency와 생성 토큰 수가 표준 디코딩보다 얼마나 늘어나는지도 별도 측정이 필요하다. 모델이 11%의 깨끗한 초안에 불필요한 편집을 한 결과는 자동 배포 시 회귀 방지 장치가 필요함을 보여준다.

코드 저장소에는 학습·평가 설정, `src/autoindexer`, tests와 Apache-2.0 라이선스가 공개돼 있다. 다만 공개 저장소의 존재는 논문 수치 재현을 뜻하지 않는다. 체크포인트·정확한 데이터 snapshot·H100 환경을 확인한 뒤 실행 가능성을 판단해야 한다.

### 실무 적용

- 대상: 코드 생성·장문 보고서 생성 시스템을 만드는 연구팀.
- 실행: 기존 모델 출력에 삽입·삭제·치환·무수정 corruption 세트를 만들고, “최종 답 정확도”와 별도로 편집 시작률, 정확 span, 불필요 편집률, 추가 토큰·지연시간을 측정한다.
- 완료 기준: 오류 유형별 최소 200개에서 baseline 재생성 방식과 비교해 순개선률이 높고, 깨끗한 입력 회귀율이 사전 임계값 이하이며, p95 지연과 GPU 메모리 증가량을 함께 기록한 표를 만든다.
- 읽는 순서: 논문 §2.1 → §2.2 → Table 2/4 → Appendix A.3–A.7 → 코드 README와 tests.

## 2. 프롬프트 최적화가 점수를 올려도 JSON 계약은 깨질 수 있다

- 원 제목: *Do Prompt Optimizers Break Requirements They Are Not Scored On? A Preregistered Study*
- 저자: Sangdo Han, Moonsoo Kim
- 공개: arXiv v1, 2026-10-09 09:38:51 UTC
- 정규 URL: https://arxiv.org/abs/2610.13287
- 코드: arXiv 페이지와 본문에서 공개 코드 저장소 링크를 확인하지 못했다.

프롬프트 최적화기는 한 개의 목표 점수를 높이도록 시스템 프롬프트를 다시 쓴다. 이 연구는 점수에 포함되지 않은 JSON 형식, 유효한 citation, 모르면 abstain, 20단어 제한이 그대로 지켜지는지를 item 단위 결정 규칙으로 검사했다. GEPA, MIPROv2, TextGrad를 HotpotQA, SQuAD 2.0, IFEval에 적용했으며 실험 가설과 판정 기준을 사전등록했다.

### 방법과 조건

HotpotQA와 SQuAD 2.0은 train 100, validation 150개로 최적화하고 test 450개와 400개로 평가했다. IFEval은 100/150/291개다. HotpotQA test에는 답변 가능 300개와 지지 문단을 제거한 150개를 포함했고, SQuAD 2.0은 가능·불가능 각 200개다. 최적화기는 정답 EM 또는 strict instruction-following만 받으며, 비채점 요구사항은 deterministic checker로 별도 계산한다.

모든 task-model 호출은 Claude Haiku 4.5, proposer 호출은 Claude Sonnet 5.5 한 공급자 조합이다. 각 run은 task-model 호출 500회, optimizer마다 3개 seed이며 1–10개 프롬프트만 탐색했다. 따라서 이 논문은 프롬프트 최적화 일반법칙이 아니라 제한된 모델·예산의 진단 연구로 읽어야 한다.

### 핵심 결과와 올바른 해석

200-token cap에서 HotpotQA exact match는 초기 0.193에서 GEPA 0.536, MIPROv2 0.406, TextGrad 0.517로 올랐다. 그러나 추출 실패율도 초기 0.7%에서 각각 27.5%, 47.0%, 13.9%가 됐다. optimized prompt가 JSON 전에 장황한 reasoning을 유도했고, parse 불가능한 QA 출력 1,629개가 모두 정확히 200토큰에서 끝났다.

citation의 순회귀는 10.7–41.6%p로 보였지만, 신규 citation 위반 1,110개 중 1,092개(98.4%)가 사실은 JSON 추출 실패였다. 양쪽 출력이 모두 parse 가능한 항목만 보면 각 요구사항의 순회귀는 3%p 이내였다. 출력 상한을 1,024토큰으로 바꾸자 4,500개 HotpotQA 응답이 모두 정상 종료·parse됐고, citation·abstain·길이 회귀는 -3.6~+0.5%p로 줄었다. 다만 “JSON 하나만 출력” 계약은 여전히 reasoning preamble 때문에 깨졌고, preamble 비율은 GEPA 38.9%, MIPROv2 62.2%, TextGrad 25.7%였다.

### 한계

1,024-token 결과와 오류 분해는 사후 분석이며 사전등록 가설의 확증 결과가 아니다. 실질적 회귀는 HotpotQA 한 과제에 집중됐고 SQuAD 2.0에서는 회귀가 없었다. 초기 프롬프트조차 code fence 때문에 strict format 검사를 90% 넘게 위반해 format 회귀를 관찰할 여지가 거의 없었다. stop reason을 저장하지 않아 200토큰 도달을 truncation의 대리 증거로 썼다. 공개 코드 링크가 없어 이번 검수에서 구현·데이터 산출물을 독립 확인하지 못했다.

### 실무 적용

- 대상: DSPy류 자동 프롬프트 최적화 또는 LLM 응답을 strict JSON으로 소비하는 팀.
- 실행: 최적화 목표와 별도로 schema parse, citation 존재·유효성, abstention, 길이, stop reason을 item 단위 회귀 테스트로 고정한다. 200/512/1024 등 여러 출력 상한에서 같은 최종 프롬프트를 다시 평가하고, tolerant extraction과 strict consumer 결과를 나눠 기록한다.
- 완료 기준: target metric 개선뿐 아니라 parse 실패율과 새 위반률의 95% 신뢰구간이 배포 임계값 안에 있고, 출력 상한 변화에도 결론이 유지된다.
- 읽는 순서: §3 Table 1–2 → §4 → §5 Table 5 → Limitations. 초록의 큰 회귀 수치만 읽지 말고 truncation 분해를 함께 본다.

## 두 논문을 함께 읽을 때

AutoIndexer는 모델 자체에 되돌아가 수정하는 능력을 넣는다. 프롬프트 최적화 연구는 더 많은 reasoning·수정이 정답률을 올려도 출력 계약과 예산을 깨뜨릴 수 있음을 보여준다. 공통 실무 원칙은 “최종 점수” 하나로 생성 시스템을 평가하지 않는 것이다. 수정 가능한 모델에는 잘못된 수정과 비용을, 최적화된 프롬프트에는 strict parse와 truncation을 별도 지표로 둬야 한다.

### 카드 2 — AutoIndexer의 발상

모델이 편집 시작·끝 위치를 직접 골라 삽입·삭제·치환합니다.

### 캡션
정답률이 높아졌다는 사실만으로 생성 시스템이 좋아졌다고 말할 수 있을까요? AutoIndexer는 이미 만든 토큰을 직접 수정하는 새 디코딩을 제안하지만, 오류 유형별 정확 복구 편차와 불필요 편집을 함께 봐야 합니다. 다른 사전등록 연구는 프롬프트 최적화가 HotpotQA 점수를 올리는 동시에 짧은 출력 예산에서 JSON 계약을 무너뜨릴 수 있음을 보였습니다. 배포 전에는 정확도와 함께 strict parse, 새 회귀, truncation, 지연시간을 고정 회귀 테스트로 관리해야 합니다.
