## 트렌드 분석

오늘 24시간의 뉴스를 관통하는 핵심 테마는 두 가지다. 첫째, 오픈웨이트 모델이 closed proprietary 모델의 아성을 실질적으로 위협하기 시작했다는 것. 둘째, AI 인프라 전반에서 inference 효율성이 새로운 경쟁의 축으로 부상하고 있다는 것이다.

GLM-5.2와 Krea 2는 서로 다른 modality를 다루지만, 같은 방향을 가리키고 있다. GLM-5.2는 753B parameter 규모에서 GPT-5.5보다 hallucination을 3배 낮추면서 benchmark 점수 차이는 4점에 불과하다는 것을 보여줬다. Krea 2는 이미지 생성 영역에서 12B parameter로 SOTA급 성능을 permissive license와 함께 공개했다. 두 모델 모두 MIT 혹은 그에 준하는 라이선스로 weights를 배포한다는 점에서, 오픈웨이트 생태계가 단순한 '저렴한 대안'을 넘어 '프로덕션 선택지'로 격상되고 있음을 시사한다. parameter scaling만으로 우위를 점하던 시대가 저물고 있다는 대형 AI 랩 내부의 회의론이 이 흐름과 맞닿아 있다.

OpenAI의 custom inference chip 'Jalapeño' 공개는 표면적으로는 다른 이야기처럼 보이지만, 실은 같은 압력에 대한 반응이다. 오픈웨이트 모델들이 비용과 통제권 측면에서 유리한 고지를 점하자, OpenAI는 하드웨어 레이어에서 inference 비용 구조 자체를 바꾸려는 전략을 택했다. performance-per-watt 개선과 coding model 특화 최적화는 API 단가 하락으로 이어질 수 있으며, 이는 오픈웨이트 진영과의 경쟁에서 closed 모델이 유지할 수 있는 마지막 레버 중 하나다. 즉, 오늘의 세 뉴스는 '오픈 vs. 클로즈드'라는 구도가 단순한 이념 논쟁이 아니라, 하드웨어·라이선스·hallucination rate까지 포함한 다층적 경쟁으로 진화했음을 보여준다.

실무자에게 주는 핵심 시사점은 명확하다. 지금 당장 프로덕션 모델 선택 기준을 재점검해야 한다. benchmark 점수 하나로 모델을 고르는 시대는 끝났다. hallucination rate, inference 비용, 라이선스 조건, fine-tuning 가능 여부를 종합한 '운영 적합성' 평가 프레임이 필요하며, GLM-5.2와 Krea 2는 그 평가를 지금 당장 시작할 수 있는 구체적인 후보다.

## 아이템 분석

### 1. GPT-5.5 hallucinates 3x more than MIT-licensed GLM-5.2

- **출처**: hackernews
- **점수**: 10.0
- **URL**: https://arrowtsx.dev/bigger-models/

**요약**

Z.ai의 MIT 라이선스 오픈웨이트 모델 GLM-5.2(753B params)가 GPT-5.5 대비 hallucination이 3배 낮으면서 벤치마크 점수는 4점 차이에 불과하다. 대형 AI 랩들 사이에서 parameter scaling 한계론이 부상하고 있다.

**맥락**

Claude Fable 5가 출시 3일 만에 미국 정부의 국가안보 우려로 사용 금지된 사건은 '무조건 크게 만들면 된다'는 scaling 패러다임의 리스크를 공론화했다. DeepSeek V4 Pro(1.6T params)가 94% hallucination rate를 기록하는 등, 대규모 factual 데이터로 훈련된 초거대 모델이 오히려 'I don't know'를 말하지 못하는 문제가 실증적으로 드러나고 있다.

**실무 시사점**

오픈웨이트 모델(GLM-5.2, MIT 라이선스)이 closed proprietary 모델과 실질적 성능 격차가 좁혀진 만큼, 프로덕션 환경에서 비용·통제권·hallucination rate를 종합 고려한 모델 선택이 필요하다. fine-tuning 및 RAG 파이프라인 설계 시 parameter 수보다 hallucination benchmark(AA-Omniscience 등)를 핵심 평가 지표로 채택하는 방향으로 전환을 검토해야 한다.

**한계 및 의문**

이 기사는 출처가 불분명한 블로그(arrowtsx.dev)로, AA Intelligence Index와 AA-Omniscience benchmark의 측정 방법론이 공개 검증되지 않았다. GPT-5.5, Claude Fable 5 등 일부 모델명은 2026년 6월 기준 가상 또는 미확인 모델일 수 있어 수치의 신뢰성을 독립적으로 확인하기 어렵다.

### 2. OpenAI unveils its first custom chip, built by Broadcom

- **출처**: hackernews
- **점수**: 8.1
- **URL**: https://techcrunch.com/2026/06/24/openai-unveils-its-first-custom-chip-built-by-broadcom/

**요약**

OpenAI가 Broadcom과 협력해 개발한 첫 번째 custom inference chip 'Jalapeño'를 공개했다. 현재 테스트 중이며, 기존 대비 performance-per-watt에서 유의미한 개선을 보인다고 밝혔다.

**맥락**

OpenAI는 그동안 Nvidia GPU에 대한 의존도가 높아 막대한 inference 비용을 지출해왔다. Google의 TPU, Amazon의 Trainium/Inferentia처럼 자체 AI accelerator를 보유한 빅테크들과 달리 OpenAI는 custom silicon이 없었고, 이번 Jalapeño 공개는 그 격차를 줄이려는 전략적 행보다.

**실무 시사점**

ML 엔지니어 입장에서 OpenAI의 inference 비용 구조가 장기적으로 개선될 수 있음을 의미하며, API 단가 하락 가능성을 염두에 두고 서비스 아키텍처를 설계할 필요가 있다. 또한 coding model 특화 inference 최적화가 강조된 만큼, real-time coding assistant 워크로드에 특히 주목할 만하다.

**한계 및 의문**

Jalapeño는 아직 테스트 단계이며 'significantly better performance-per-watt'라는 주장은 독립적으로 검증되지 않았다. 실제 production 배포 일정과 범용 모델 지원 여부도 불명확해 단기적 영향은 제한적일 수 있다.

### 3. Krea 2: SOTA open-weights 12B image model

- **출처**: hackernews
- **점수**: 7.7
- **URL**: https://www.krea.ai/blog/krea-2-technical-report

**요약**

Krea가 120억 파라미터 규모의 오픈 웨이트 이미지 생성 foundation model인 Krea 2를 공개했다. permissive license 하에 weights와 코드를 모두 배포하며, 미적 다양성과 사용자 creative control을 핵심 설계 원칙으로 삼는다.

**맥락**

Stable Diffusion 이후 오픈 이미지 생성 모델 생태계는 FLUX, SD3 등으로 발전해왔으나, 대부분의 SOTA 모델이 특정 aesthetic에 수렴하는 문제가 지적되어 왔다. 동시에 Midjourney, Adobe Firefly 등 상용 모델이 creative control 측면에서 우위를 점하는 상황에서, 12B 규모의 오픈 웨이트 모델 등장은 커뮤니티에 중요한 전환점이 될 수 있다.

**실무 시사점**

Hugging Face에서 weights를 직접 다운로드할 수 있으므로, fine-tuning 및 LoRA 실험을 즉시 시작할 수 있다. permissive license 덕분에 상업적 프로젝트에도 활용 가능하며, multi-stage training pipeline과 distributed infrastructure 설계 내용이 기술 보고서에 공개되어 있어 대규모 이미지 모델 학습을 연구하는 ML 엔지니어에게 실질적인 참고 자료가 된다.

**한계 및 의문**

기술 보고서가 58분 분량의 장문임에도 벤치마크 비교 데이터와 독립적인 third-party 평가가 아직 부족하며, 'SOTA'라는 주장이 자체 평가에 기반한 것인지 외부 검증을 거친 것인지 불분명하다. 또한 12B 파라미터 모델의 inference 비용이 일반 개발자 환경에서 현실적으로 감당 가능한지도 확인이 필요하다.
