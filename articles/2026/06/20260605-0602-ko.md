# LLM이 해킹한다? 보안 자동화의 기대와 현실

> **리포트 ID**: `20260605-0602`  
> **생성**: 2026-06-05 06:02 UTC  
> **아이템**: 3개  

## 트렌드 분석

오늘 뉴스의 핵심 테마는 두 가지다. 첫째, LLM의 보안 영역 진출이 본격화되고 있다는 것. 둘째, 그 진출이 기대만큼 매끄럽지 않다는 것. Anthropic의 오픈소스 framework 공개와 한 개발자의 $1,500짜리 실험은 같은 질문을 서로 다른 각도에서 던지고 있다. "LLM이 실제로 코드 보안을 책임질 수 있는가?"

Anthropicは 'defending-code-reference-harness'를 통해 LLM 기반 automated vulnerability discovery를 공식 도구로 제시했다. 이는 보안 자동화에 대한 업계의 신뢰를 높이는 방향의 움직임이다. 그러나 같은 날 공개된 실험 결과는 냉정한 반론을 제시한다. 의도적으로 취약하게 설계된 앱에서 Firebase Broken Access Control 취약점을 LLM이 자동으로 발견·익스플로잇하는 데 실패했다는 것이다. framework가 존재한다는 것과, 그 framework가 실전에서 작동한다는 것은 전혀 다른 이야기다. 두 아이템은 "가능성"과 "현실" 사이의 간극을 동시에 보여준다.

여기에 Google DeepMind의 Gemma 4 12B가 흥미로운 맥락을 추가한다. encoder 없이 vision과 audio를 LLM backbone에 직접 통합한 unified multimodal architecture는, 보안 분야에서도 코드뿐 아니라 UI 스크린샷이나 로그 오디오까지 분석 범위를 넓힐 수 있는 기술적 토대를 제공한다. 메모리 효율을 높여 노트북에서도 실행 가능한 수준을 목표로 한다는 점은, 보안 도구의 on-premise 배포 가능성을 열어준다. 즉, Gemma 4의 방향성은 오늘의 보안 자동화 논의와 중장기적으로 연결된다.

실무자에게 주는 핵심 시사점은 명확하다. LLM 기반 보안 자동화 도구를 도입할 때, 현재 단계에서는 "탐지 보조 도구"로 포지셔닝해야 하며 단독 방어선으로 신뢰해서는 안 된다. Anthropic의 framework는 출발점이지 완성형이 아니다. Firebase Security Rules처럼 API 레이어 뒤에 숨은 취약점은 여전히 사람의 눈이 필요하다. LLM의 capability가 빠르게 성장하고 있지만, 지금 당장의 benchmark는 실전 환경에서 과대평가되기 쉽다.

## 아이템 분석

### 1. Anthropic's open-source framework for AI-powered vulnerability discovery

- **출처**: hackernews
- **점수**: 7.6
- **URL**: https://github.com/anthropics/defending-code-reference-harness

**요약**

Anthropic이 AI 기반 취약점 탐지를 위한 오픈소스 framework인 'defending-code-reference-harness'를 공개했다. 이 도구는 LLM을 활용해 코드 보안 취약점을 자동으로 발견하는 것을 목표로 한다.

**맥락**

최근 LLM의 코드 이해 능력이 급격히 향상되면서, AI를 활용한 보안 취약점 탐지(vulnerability discovery)가 주목받고 있다. 기존의 static analysis나 fuzzing 기반 도구의 한계를 LLM이 보완할 수 있다는 기대가 커지는 시점에 Anthropic이 직접 reference harness를 공개한 것은 의미가 크다.

**실무 시사점**

보안 엔지니어와 ML practitioner는 이 framework를 자신의 코드베이스에 적용해 LLM 기반 취약점 탐지 파이프라인을 실험해볼 수 있다. 특히 Claude API와의 통합 방식을 참고해 자체적인 automated security review 워크플로우를 구축하는 데 활용할 수 있으며, CI/CD 파이프라인에 통합하는 방향도 고려할 만하다.

**한계 및 의문**

LLM 기반 취약점 탐지는 false positive 비율이 높을 수 있고, 복잡한 multi-file 의존성이나 runtime context가 필요한 취약점은 놓칠 가능성이 있다. 또한 공개된 정보가 제한적이어서 실제 탐지 성능(recall, precision)에 대한 벤치마크 데이터가 부족하다.

**관련 링크**

- https://github.com/anthropics/defending-code-reference-harness

### 2. Gemma 4 12B: A unified, encoder-free multimodal model

- **출처**: hackernews
- **점수**: 7.5
- **URL**: https://blog.google/innovation-and-ai/technology/developers-tools/introducing-gemma-4-12b/

**요약**

Google DeepMind이 Gemma 4 12B를 출시했다. encoder 없이 vision과 audio input을 LLM backbone에 직접 통합한 unified multimodal 아키텍처가 특징이며, 노트북에서 실행 가능한 수준의 메모리 효율을 목표로 한다.

**맥락**

온디바이스 AI 경쟁이 심화되는 가운데, Gemma 시리즈는 이미 1억 5천만 다운로드를 돌파했다. 기존 multimodal 모델들이 별도의 vision encoder(예: CLIP)를 사용하는 것과 달리, encoder-free 통합 아키텍처는 구조적 단순화와 latency 감소를 동시에 노린 설계로 주목받고 있다.

**실무 시사점**

ML 엔지니어는 encoder-free unified architecture가 기존 vision-language model 파이프라인 대비 inference 비용과 메모리 사용량에 어떤 차이를 만드는지 직접 벤치마킹해볼 필요가 있다. 또한 native audio input 지원이 추가된 만큼, 음성 기반 agentic 애플리케이션 프로토타이핑에 Gemma 4 12B를 우선 검토할 수 있다.

**한계 및 의문**

벤치마크 성능이 26B MoE 모델에 '근접'한다고 표현하지만 구체적인 수치와 평가 태스크가 공개되지 않아 독립적인 검증이 필요하다. encoder-free 설계가 실제로 다양한 도메인의 vision·audio 이해 품질에서 encoder 기반 모델과 동등한지는 추가 연구가 요구된다.

**관련 링크**

- https://blog.google/innovation-and-ai/technology/developers-tools/introducing-gemma-4-12b/

### 3. I built a vulnerable app and spent $1,500 seeing if LLMs could hack it

- **출처**: hackernews
- **점수**: 7.4
- **URL**: https://kasra.blog/blog/i-spent-1500-seeing-if-llms-could-hack-my-app/

**요약**

개발자가 의도적으로 취약한 앱을 만들고 주요 LLM들이 Firebase Broken Access Control 취약점을 자동으로 발견·익스플로잇할 수 있는지 $1,500을 써서 실험했다. 결과적으로 LLM의 보안 취약점 탐지 능력에 현실적인 한계가 드러났다.

**맥락**

LLM 기반 자동화 보안 테스트(pen-testing) 도구에 대한 관심이 급증하는 시점에서, 실제 현장에서 자주 발견되는 Firebase/Supabase의 Broken Access Control 취약점을 LLM이 얼마나 재현할 수 있는지 검증하는 실험이다. APK 리버싱 후 google-services.json을 통해 Firebase에 직접 sign-up하고 Firestore를 읽는 패턴은 실제 앱 감사에서 반복적으로 발견되는 취약점 클래스다.

**실무 시사점**

Firebase나 Supabase를 data layer로 사용하는 앱을 개발 중이라면, API 레이어만 hardening하고 Firebase Security Rules를 방치하는 패턴이 얼마나 위험한지 재확인해야 한다. 또한 LLM을 보안 자동화 도구로 도입할 때 현재 수준에서는 복잡한 multi-step exploit chain을 완전히 자율 수행하기 어렵다는 점을 감안해 human-in-the-loop 구조를 유지해야 한다.

**한계 및 의문**

저자 본인이 명시했듯 이 실험은 scientific eval이 아니며, LLM별 10회 실행을 목표로 했으나 비용 문제로 중단됐다. 샘플 수가 적고 통제 변수가 부족해 결과를 일반화하기 어렵고, 사용된 LLM 버전·프롬프트 전략에 따라 결과가 크게 달라질 수 있다.

**관련 링크**

- https://kasra.blog/blog/i-spent-1500-seeing-if-llms-could-hack-my-app/
