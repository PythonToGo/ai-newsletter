# Agent 시대의 인프라 전쟁: 통신·CI·오케스트레이션이 동시에 흔들린다

## 트렌드 분석

오늘 24시간의 뉴스를 관통하는 핵심 테마는 하나다: AI agent가 '실험'에서 '운영'으로 넘어가는 순간, 기존 인프라가 일제히 병목으로 드러나고 있다는 것. Cache-to-Cache 통신 연구, Linear 팀의 CI 재설계, 그리고 Google의 AX 공개는 각각 다른 레이어의 문제를 다루지만, 모두 같은 질문에 답하려 한다: 'agent가 대규모로 작동할 때 무엇이 부서지는가?'

세 아이템은 agent 파이프라인의 서로 다른 레이어를 공략한다. Cache-to-Cache는 모델 간 통신 레이어를 겨냥한다. 현재 multi-agent 시스템은 LLM끼리 텍스트를 직렬화해 주고받는데, 이는 token 생성 비용과 latency를 그대로 누적시킨다. KV cache를 직접 교환하면 이 overhead를 근본적으로 제거할 수 있다. 한편 Google의 AX는 실행 레이어를 표준화한다. Kubernetes의 선언적 YAML 철학을 agent orchestration에 이식함으로써, sandbox 격리·네트워크 분리·클러스터 병렬 실행을 인프라 팀이 익숙한 방식으로 다룰 수 있게 한다. 그리고 Linear의 CI 재설계는 코드 생성 레이어의 downstream 충격을 보여준다. AI coding agent가 PR 수를 폭발적으로 늘리자, 사람이 설계한 CI 파이프라인이 즉시 병목이 됐다.

흥미로운 점은 이 세 가지가 서로 다른 시간 지평에 놓여 있다는 것이다. Cache-to-Cache는 아직 연구 단계로, 동일 아키텍처 모델 간 호환성 문제가 해결되지 않았다. AX는 오픈소스로 공개됐지만 프로덕션 성숙도는 검증이 필요하다. 반면 Linear의 CI 문제는 이미 현실이다. 즉, agent로 인한 인프라 압박은 지금 당장 코드 레이어에서 시작해 점차 실행·통신 레이어로 전파되고 있는 것이다.

실무자에게 주는 시사점은 명확하다: agent를 도입하기 전에 현재 CI/CD pipeline의 critical path를 먼저 측정하라. AI가 생성하는 코드는 사람보다 빠르고 많지만, 그것을 검증하는 인프라가 따라가지 못하면 오히려 delivery 속도가 역전될 수 있다. AX 같은 orchestration 레이어와 Cache-to-Cache 같은 통신 최적화는 중기 투자로 모니터링하되, 지금 당장은 test sharding·incremental build·runner 캐싱부터 손대야 한다.

### 1. Cache-to-Cache: Direct Semantic Communication Between LLMs (2025)

- **출처**: hackernews
- **점수**: 7.5
- **URL**: https://arxiv.org/abs/2510.03215

**요약**

LLM 간 KV cache를 직접 교환해 semantic 정보를 전달하는 Cache-to-Cache 통신 방식을 제안. 텍스트 직렬화 없이 모델 간 직접 소통으로 효율성을 높인다.

**맥락**

멀티 에이전트 LLM 시스템이 확산되면서 모델 간 통신 오버헤드가 병목으로 부상했다. 기존에는 LLM 출력을 텍스트로 직렬화해 다음 모델에 전달했으나, 이 과정에서 semantic 정보 손실과 latency 증가가 발생한다.

**실무 시사점**

멀티 에이전트 파이프라인을 구축하는 엔지니어라면 KV cache 공유 방식이 실용화될 경우 inter-model 통신 비용을 크게 줄일 수 있음을 주목해야 한다. 현재는 연구 단계이지만, 동일 아키텍처 모델 간 cache 재사용 가능성을 실험해볼 가치가 있다.

**한계 및 의문**

동일하거나 호환 가능한 아키텍처 간에만 적용 가능하다는 근본적 제약이 있으며, 서로 다른 모델 패밀리 간 일반화 가능성은 아직 검증되지 않았다.

**관련 링크**

- https://arxiv.org/abs/2510.03215

### 2. AI coding has made CI a bottleneck, so we reworked ours to keep up

- **출처**: hackernews
- **점수**: 7.3
- **URL**: https://linear.app/now/ci-bottleneck-reworked

**요약**

AI 코딩 agent의 급증으로 PR 수가 폭발적으로 늘어나면서 CI가 병목이 된 Linear 팀이, 인프라 업그레이드·job 최적화·setup 중복 제거·test 실행 효율화를 통해 PR 대기 시간을 6분에서 5분으로 줄이고 runner 시간을 절반으로 단축했다.

**맥락**

2025~2026년 들어 Cursor, Copilot Workspace 등 AI coding agent가 실무에 본격 도입되면서 개발자 1인당 PR 생성 속도가 수배 이상 빨라졌다. 코드 생성 속도는 agent가 따라잡았지만, 모든 PR이 통과해야 하는 CI 파이프라인은 기존 속도 그대로여서 인프라 비용 급등과 feedback loop 지연이 현장 문제로 부상하고 있다.

**실무 시사점**

ML/백엔드 팀은 지금 당장 CI job 의존 그래프를 분석해 critical path를 단축하고, test sharding·캐싱·incremental build를 도입해야 한다. 특히 agent가 생성한 코드는 사람보다 test coverage가 넓어질 수 있으므로, runner 비용 모니터링과 flaky test 제거를 CI 최적화의 우선순위로 올려야 한다.

**한계 및 의문**

Linear의 사례는 TypeScript 모노레포 환경에 특화되어 있어 Python·다중 언어 ML 파이프라인에 그대로 적용하기 어려울 수 있다. 또한 PR 대기 시간 1분 단축이라는 수치가 agent 도입 규모나 팀 구조에 따라 실제 체감 효과와 다를 수 있으며, test 품질(false negative 감소 등) 지표는 공개되지 않았다.

**관련 링크**

- https://linear.app/now/ci-bottleneck-reworked

### 3. AX – Google’s Open Agentic Orchestrator

- **출처**: hackernews
- **점수**: 7.2
- **URL**: https://agentexecutor.io

**요약**

Google이 오픈소스 agentic orchestrator인 AX를 공개했다. Kubernetes 스타일의 YAML로 task를 선언하면 AX가 sandbox 환경에서 네트워크 격리와 workspace를 자동 구성해 대규모 agent task를 클러스터에서 실행한다.

**맥락**

LLM 기반 agent 시스템이 단순 챗봇을 넘어 코드 실행, 파일 조작, 외부 API 호출 등 복잡한 작업을 수행하는 방향으로 빠르게 진화하면서, 이를 안전하고 확장 가능하게 orchestration하는 인프라 레이어의 필요성이 커지고 있다. Kubernetes 생태계에 익숙한 엔지니어들이 agent workload도 동일한 패러다임으로 관리할 수 있도록 Google이 AX를 오픈소스로 공개한 시점은 이 흐름과 맞닿아 있다.

**실무 시사점**

ML 엔지니어와 DevOps 팀은 AX의 YAML 기반 선언적 API를 활용해 기존 Kubernetes 클러스터 위에서 agent task를 sandbox로 격리하고 대규모 병렬 실행 파이프라인을 빠르게 구성할 수 있다. `ax ssh`, `ax suspend`, `ax resume` 등의 CLI 명령어로 실행 중인 agent 상태를 직접 디버깅할 수 있어 production 환경에서의 observability 확보가 용이하다.

**한계 및 의문**

현재 `ax.io/v1alpha1` API 버전에서 알 수 있듯 아직 alpha 단계이며 production 안정성과 장기 지원 여부가 불확실하다. 네트워크 fencing이나 sandbox 보안 모델의 구체적인 구현 세부사항이 공개 문서에서 충분히 검증되지 않아 보안 민감 환경에서의 적용에는 추가 검토가 필요하다.

**관련 링크**

- https://agentexecutor.io
- https://github.com/golang/go
