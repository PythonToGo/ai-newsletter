## 트렌드 분석

오늘은 다국어 번역 모델, 로봇의 장애물 회피 학습, 영상 생성의 메모리 절약 실행을 다룬다. Tencent는 번역 가중치와 평가 자원을 공개했고, NVIDIA의 두 개발 가이드는 각각 보행 정책 위에 회피 제어를 더하는 방법과 GPU 밖에 가중치를 두는 방법을 설명한다. 모델 출시와 튜토리얼 공개는 다른 사건이며 하나의 성능 순위로 묶지 않는다.

편집 관점의 공통점은 모델 이름보다 사용 조건이 중요하다는 것이다. 번역은 자연스러운 문장뿐 아니라 변수·서식을 보존해야 하고, 로봇은 걷기와 장애물 인지가 서로 다른 주기로 동작한다. GPU 메모리를 줄여도 시스템 RAM과 기다리는 시간은 늘 수 있다. 성능·통합 비용·운영 제약을 나눠 읽어야 한다.

최근 14일 뉴스 아카이브 18개 보고서의 제목·URL·사건과 최근 7일 주제 구성을 대조했다. AI·ML·딥러닝·비전·로보틱스·인프라를 넓게 탐색했고, 이미 소개한 RoboTrack·Ling-3.2-air·Decart 계약은 반복하지 않았다. 아래 원문은 모두 **2026-11-24** 공개·게시를 명시한다. 정확한 원문 게시 시각은 확보하지 못했으므로 엄밀한 24시간 경계 안인지까지 단정하지 않는다.

점수는 중요성·신규성·근거 수준을 반영한 **편집 선정 점수(0–10)**다. 공급자 수치는 독립 재현 결과가 아니며, 확인일은 모두 2026-11-25이다. 이번 작성에서 모델 추론·학습·유료 API를 실행하지 않았다.

### 1. Hy-MT3 공개: 102개 언어 번역, 문장 품질과 형식 보존을 함께 본다

- **출처**: Tencent Hunyuan 공식 GitHub·Hugging Face 모델 카드
- **점수**: 8.4/10 — 편집 선정 점수
- **URL**: https://github.com/Tencent-Hunyuan/Hy-MT3

**요약**

Tencent가 11월 24일 번역 특화 Hy-MT3의 1.8B·7B·30B-A3B 가중치와 TransRubric 평가 자원을 공개했다. 언어 지원은 Hy-MT2의 38개에서 102개로 늘었으며 한국어도 포함한다. 30B-A3B는 전체 약 300억 파라미터 중 토큰마다 약 30억을 활성화하는 전문가 혼합(MoE) 모델이다. 공식 목록에는 FP8·GGUF 배포판과 학습·추론 안내가 있으며, 확인한 30B-A3B 모델 카드는 Apache 2.0을 표기한다.

**맥락**

공급자는 실사용 시나리오 데이터에서 이전 Hy-MT2 대비 오역이 있는 표본 비율이 43%, 누락·추가 오류가 74%, 지시 준수 오류가 40% 감소했다고 보고한다. 이는 **오류 비율의 상대 감소**이지 전체 번역 정확도가 그만큼의 퍼센트포인트 상승했다는 뜻은 아니다. 이 소개만으로 절대 오류율이나 언어별 품질을 확정할 수 없다.

이번 공개는 번역 평가의 기준표도 제공한다. TransRubric은 원문·번역문·지시와 표본별 체크리스트를 읽고 오류 유형·심각도·0–100점 점수를 내도록 하는 LLM 평가 방식이다. 일반 번역 종합 수치에는 이 공급자 평가 방식이 쓰였다. “사람보다 낫다”는 포괄적 결론으로 확대하지 않고, 자사 문서의 오류를 설명하는 보조 도구로 보는 편이 적절하다.

**실무 시사점**

다국어 제품·게임 현지화 팀은 용어집, 변수 자리표시자, 태그, 숫자, 번역 금지 키가 포함된 고정 표본을 먼저 만들자. 기존 번역기와 같은 입력·출력 한도에서 의미 보존과 형식 오류를 따로 비교하고, 중요 표본은 해당 언어 검토자가 확인한다. 완료 기준은 평균 점수만이 아니라 누락·변수 손상·잘못된 언어 출력이 정한 허용 수준을 만족하는 것이다.

공식 프롬프트 예제는 목표 언어의 전체 이름과 출력 제약을 명시한다. 문맥 한도는 8,192로 안내되므로 긴 문서를 한 번에 넣기보다 구간 분할과 용어 일관성을 함께 설계해야 한다. 활성 파라미터 3B를 전체 가중치 저장량이나 실제 서버 메모리로 오인하지 않는 것도 중요하다.

**한계 및 의문**

공급자 자체 평가이며 이번에는 독립 번역 테스트를 실행하지 않았다. 102개 언어 지원은 모든 방향·분야에서 같은 품질이라는 뜻이 아니다. 공개 TransRubric 자원도 모든 언어 쌍을 같은 수로 포함하지 않고, 평가 프롬프트·기준표 공개가 무료 판정 모델 제공을 의미하지는 않는다. 양자화 배포판별 품질도 별도 확인이 필요하다.

**관련 링크**

- [공식 공개 기록·평가 설명·배포 안내](https://github.com/Tencent-Hunyuan/Hy-MT3) — 원 게시자 Tencent Hunyuan. 공개 사건일 2026-11-24.
- [30B-A3B 공식 모델 카드](https://huggingface.co/tencent/Hy-MT3-30B-A3B) — 가중치 배포·라이선스 표기 확인.
- [TransRubric 자원·범위·판정 방식](https://github.com/Tencent-Hunyuan/Hy-MT3/blob/main/TransRubric/README.md).

### 2. Microduck 회피 학습 가이드: 걷기는 고정하고 센서로 명령을 조정한다

- **출처**: Hugging Face의 NVIDIA 공식 개발 글·Isaac Lab 배포 문서
- **점수**: 7.8/10 — 편집 선정 점수
- **URL**: https://huggingface.co/blog/nvidia/microduck-obstacle-avoidance

**요약**

NVIDIA가 11월 24일 Microduck의 시뮬레이션 학습부터 실제 장애물 회피 시험까지 이어지는 가이드를 공개했다. 기존 보행 정책은 고정하고 별도 정책이 게임패드의 이동 명령을 조정한다. ToF는 빛의 왕복 시간으로 거리를 재는 센서이며, 여기서는 8×8 격자를 15Hz로 읽는다. 회피 정책은 50Hz로 명령을 조정하므로 두 주기를 같은 것으로 읽으면 안 된다.

**맥락**

학습 예제는 PPO 강화학습을 사용하며 16,384개 병렬 환경·1,500회 업데이트를 안내한다. 이는 최소 하드웨어 요건이 아니다. 별도 DGX Spark 구성에서는 4,096개 환경·3,000회 업데이트로 약 6시간 학습했다고 보고한다. 환경 수·업데이트 수가 다르므로 두 구성을 동일 조건 속도 경쟁으로 비교하지 않는다.

편집 해석: 이 소식의 가치는 새 범용 로봇 모델 발표보다, 이미 걷는 로봇에 센서 기반 상위 제어를 붙이는 구체적 경로에 있다. 보행 자체를 다시 학습하지 않는다고 해서 센서 배치·지연·누락의 차이가 사라지는 것은 아니다.

**실무 시사점**

소형 로봇 학습 팀은 먼저 문서의 실험 브랜치와 자산 버전, 학습 때 쓴 보행 정책을 고정하자. 배포 README의 dry-run은 로봇을 움직이지 않고 센서와 제안 명령을 확인하는 단계다. 이를 통과한 뒤 별도의 감독 시험에서 정지 동작과 장애물 접근을 점검하는 순서가 적절하다.

완료 기준은 보기 좋은 회피 영상 하나가 아니라 새로운 배치에서의 충돌·넘어짐·불필요한 정지와 센서 지연 기록을 함께 남기는 것이다. 실제 배포는 노트북에서 회피 모델을 실행하고 로봇에 조정된 명령을 보낸다. 통신 이상까지 포함한 시험 계획이 필요하다.

**한계 및 의문**

가이드는 범용 자율주행이나 검증된 안전 장치를 제공하지 않는다. 공식 배포 문서는 기본 전진 속도 0.15m/s 제한, 오래된 센서 입력에 대한 정지, 중앙 ToF 거리 0.20m 이내의 추가 제동을 설명한다. 그러나 **후진에는 회피를 적용하지 않으며 수동 운전은 회피·추가 제동을 우회**한다. 이 제한을 숨긴 채 “충돌 방지 로봇”으로 소개하면 안 된다.

원문은 학습·시연 경로를 보여주지만 여러 실제 환경에 걸친 성공률과 신뢰구간을 제공하지 않는다. 이번에는 문서만 확인했고 로봇이나 학습 코드를 실행하지 않았다.

**관련 링크**

- [Isaac Lab 실험 브랜치의 실제 배포 README](https://github.com/isaac-sim/IsaacLab/blob/exp/microduck/scripts/deploy/microduck_tof_nav/README.md) — 노트북·로봇 역할, 제어·정지·우회 조건.

### 3. Cosmos 3 Nano의 12GB GPU 실행: 메모리는 줄이고 기다림은 감수한다

- **출처**: NVIDIA Technical Blog·Cosmos-Framework 공식 문서
- **점수**: 8.0/10 — 편집 선정 점수
- **URL**: https://developer.nvidia.com/blog/how-to-run-nvidia-cosmos-3-on-local-ai-devices-using-hugging-face-diffusers/

**요약**

NVIDIA가 11월 24일 Cosmos 3 Nano를 12GB급 GPU에서 실행하는 가이드를 공개했다. 새 모델 출시가 아니라 기존 모델의 실행 경로를 설명하는 소식이다. 가중치를 시스템 RAM에 두고 필요한 블록을 GPU로 옮기며 계산은 CUDA에서 한다. 디스크에서 매번 직접 읽는 방식도, CPU만으로 추론하는 방법도 아니다.

**맥락**

공급자 표에서 RTX 5070의 1280×720 텍스트→영상 생성은 BF16 기준 **2,624.9초·최대 9.94GiB**, 혼합 FP8 기준 **2,235.7초·9.16GiB**다. 189프레임·24fps, 35단계 생성 조건이며 호스트는 약 128GB RAM이다. 측정은 파이프라인 호출이며 가중치 로딩과 MP4 인코딩은 제외한다. 약 8초 분량의 영상에 수십 분이 걸리는 사례로, 실시간 실행을 뜻하지 않는다.

128GB는 시험 구성이지 측정된 최소 RAM이 아니다. 또한 FP8 경로도 모든 연산이 8비트인 것은 아니며 attention은 BF16을 사용한다. GPU에 들어간다는 사실과 원하는 시간 안에 결과를 받는다는 사실을 구분해야 한다.

**실무 시사점**

로컬 영상 생성·합성 데이터 팀은 모델과 보호 모델의 접근 조건, RAM·디스크·PCIe 여유를 먼저 확인하자. 후속 검증에서는 한 모달리티·낮은 해상도로 시작하고 입력·프레임·정밀도·소프트웨어 리비전을 고정하는 편이 좋다. 완료 기준은 최대 GPU 메모리뿐 아니라 전체 대기 시간과 결과물 품질을 함께 기록해 실제 작업 예산을 만족하는 것이다.

공식 벤치마크 문서는 단일 실행 시간을 예열된 반복 측정의 중앙값과 구별하고, 로딩·인코딩 시간을 따로 기록한다. 이에 맞춰 모델 로드부터 파일 저장까지의 총시간도 별도 측정하자. 이번에는 문서만 읽었으며 체크포인트 다운로드나 벤치마크를 실행하지 않았다.

**한계 및 의문**

서로 다른 호스트의 단발 측정이므로 통제된 GPU 순위나 FP8 품질 동등성의 증거가 아니다. 가이드의 Transfer 행 일부는 보호 검사 비활성 조건으로 표시돼 있어 일반 텍스트→영상 행과 섞어 비교하면 안 된다. 이번 소개의 수치는 기본 검사를 켠 텍스트→영상 조건이다.

공식 README는 단일 파이프라인 인스턴스의 동시 호출을 지원하지 않고 순차 호출하도록 안내한다. 작은 GPU용 메모리 절약을 곧바로 다중 사용자 서비스의 처리량 개선으로 옮겨 해석하지 않는다.
