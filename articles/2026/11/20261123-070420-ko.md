## 트렌드 분석

### 1. Sarvam-105B-1711: API 이름은 그대로, 비교해야 할 가중치는 바뀌었다

- **출처**: Sarvam AI 공식 발표·API 변경 이력·Hugging Face 모델 카드
- **점수**: 8.2/10 — 편집 선정 점수
- **URL**: https://www.sarvam.ai/blogs/sarvam-105b-1711

**요약**

Sarvam AI가 11월 22일 Sarvam-105B-1711을 공개했다. 기존 105B 모델을 추가 후학습한 체크포인트이며, 공개 카드는 총 1,050억·토큰당 활성 103억 파라미터의 MoE 구조를 설명한다. BF16과 NVFP4 가중치가 별도로 배포됐다. 같은 날 API 변경 이력은 `sarvam-105b`와 `sarvam-105b-conversations`가 새 가중치를 사용하며 식별자·엔드포인트·요청 형식은 바뀌지 않는다고 안내한다.

**맥락**

이 소식의 운영상 핵심은 ‘호출 코드를 바꾸지 않아도 모델의 동작은 바뀐다’는 점이다. 배포 전후 성능을 비교할 때 모델 이름만 기록했다면 어떤 가중치에서 나온 결과인지 구분하기 어렵다. 이는 API가 깨지는 변경과는 다른 종류의 회귀 점검을 요구한다.

게시자 모델 카드의 τ²-Bench 평균 보상은 BF16 **85.5**, NVFP4 **84.1**이다. 항공·소매·통신 과제, 사용자 시뮬레이터 GPT-5.2 low, 최대 200단계 조건의 자체 평가다. 정밀도별 수치가 다르므로 BF16 점수를 4비트 배포판의 결과로 옮겨 적지 않았다. 공식 블로그와 모델 카드의 일부 정밀도별 수치 표기가 일치하지 않아, 이번 호는 정밀도를 나눠 제시한 모델 카드의 표를 기준으로 읽는다.

**실무 시사점**

대상은 다국어 상담·도구 호출 시스템의 모델 교체를 담당하는 팀이다. 먼저 기존 결과와 새 체크포인트 결과를 구분할 버전 기록을 준비하고, 실제 업무와 유사한 고정 대화에서 지시 준수·도구 인자·반복 실행 성공을 별도로 비교하자. 자체 배포를 검토한다면 BF16과 NVFP4를 같은 프롬프트·도구 예산으로 평가하고, 모델 카드의 권장 런타임과 출력 파서도 함께 고정해야 한다.

완료 기준은 종합 점수 상승이 아니라 중요한 업무별 회귀가 허용 범위 안인지, 같은 조건에서 여러 번 성공하는지, 파싱 실패가 없는지를 설명할 수 있는 것이다. 자동 교체된 API를 사용 중이라면 ‘코드 변경 없음’을 ‘재검증 불필요’로 해석하지 않는 것이 좋다. 이번에는 문서와 공개 설정만 읽었으며 유료 API나 모델 추론을 실행하지 않았다.

**한계 및 의문**

평가는 공급자 자체 실행이며 독립 재현 결과가 아니다. 내부 Indic 평가와 공개 벤치마크도 같은 의미의 일반화 증거가 아니다. 한 정밀도에서의 향상을 다른 정밀도·대화 길이·언어·실행 도구 구성에 그대로 적용할 수 없다. 가중치 저장소는 Apache 2.0을 표기하지만, 실제 운영 비용은 장비·문맥 길이·동시 사용자에 따라 별도 검토가 필요하다. 정확한 공식 게시 시각은 미표기다.

**관련 링크**

### 2. Frontia VAD 2.3: 한 모델로 실시간·녹음을 처리하되, 후처리 지연은 남는다

- **출처**: ESPnet 공식 Hugging Face 모델 카드·공개 커밋
- **점수**: 7.5/10 — 편집 선정 점수
- **URL**: https://huggingface.co/espnet/frontia_vad_v2_3

**요약**

ESPnet이 11월 22일 Frontia VAD 2.3 가중치와 설정을 공개했다. VAD는 음성을 문자로 전사하는 모델이 아니라 ‘누군가 말하고 있는 구간’을 찾는 기능이다. 이전 계열의 모드별 모델 대신 단일 TCN, 즉 시간축 합성곱 신경망이 실시간·오프라인 모드를 함께 지원한다. 실시간 모드의 모델 look-ahead는 0, 오프라인은 124프레임·약 0.99초이며, 여러 화자는 하나의 발화 라벨로 합친다.

**맥락**

모델 입력의 미래 참조와 최종 판정 지연은 다르다. 카드는 16kHz 입력에서 512샘플 분석 창·128샘플 이동 간격을 사용한다. 창을 모으는 데 32ms가 필요하고, 권장 실시간 후처리인 중앙 정렬 25프레임 median 필터는 이후 12프레임, 즉 96ms를 더 기다린다. 합계 약 **128ms**는 카드에서 계산한 프레임 시작 기준 지연이지 마이크부터 앱 응답까지의 실측값이 아니다.

미래 참조를 줄인 신경망만 보고 ‘무지연’이라고 부르면 후처리의 시간 예산을 놓친다. 반대로 필터를 없애면 지연은 줄겠지만 오검출과 경계 흔들림이 어떻게 변할지는 별도 측정해야 한다.

**실무 시사점**

음성 인터페이스나 녹음 전처리 담당자는 같은 오디오에서 모드·임계값·평활화 설정을 구분한 평가 계획을 세우자. 말 시작을 놓치는 비율, 무음의 오검출, 짧은 발화의 손실, 판정 지연을 따로 기록한다. 완료 기준은 가중치를 하나로 통합했다는 사실이 아니라 서비스의 지연 한도 안에서 허용 가능한 검출 오류를 유지하는 것이다.

공식 카드는 기존 `DiarizeSpeech`로 프레임별 발화 확률을 받고 판정 규칙은 직접 적용하도록 안내한다. 준비 중인 `espnet detect` 편의 래퍼가 이미 배포됐다고 가정하지 않아야 한다. 이번에는 공개 카드와 추론 인터페이스 코드를 확인했으며 음성 데이터나 모델을 실행하지 않았다.

**한계 및 의문**

이 체크포인트의 검출 오류 표는 아직 없으며 v1 평가 세트에서도 채점하지 않았다고 카드가 명시한다. 개발 세트에서 조정한 임계값이 다른 언어·배경음·마이크에서도 적절한지는 확인되지 않았다. 발화 검출은 화자 식별이나 받아쓰기 정확도를 보장하지 않는다.

라이선스 표기도 버전 확인이 필요하다. 초기 공개 커밋의 README 메타데이터는 CC BY-SA 4.0, 현재 페이지 배지는 CC BY 4.0으로 달라 보인다. 이번 호는 어느 표기가 전체 배포물에 적용되는지 확정하지 않고, 사용하는 리비전의 조건을 확인할 과제로 남긴다. 공개일은 확인했지만 정확한 UTC 게시 시각은 확보하지 못했다.

### 3. AMD의 Granite 4.2 8B 압축판: CPU 배포에서 용량·정확도·실행 경로를 나눠 본다

- **출처**: AMD 공식 Hugging Face 카드·가중치 업로드
- **점수**: 7.6/10 — 편집 선정 점수
- **URL**: https://huggingface.co/amd/granite-4.2-8b-w4a16-llmcompressor

**요약**

AMD가 11월 22일 IBM Granite 4.2 8B의 EPYC CPU용 압축 체크포인트를 공개했다. 새 기반 모델이 아니라 기존 모델을 GPTQ 방식으로 양자화한 배포판이다. W4A16은 가중치 4비트·활성값 16비트 구성을 뜻하며, 일부 임베딩·출력 계층은 BF16으로 유지한다. 카드는 Linux와 ZenDNN·ZenTorch·vLLM 조합을 안내하며 GPU용으로 설계한 배포판은 아니라고 명시한다.

**맥락**

게시자 보고에서 디스크 가중치는 **16.4GiB → 5.4GiB**로 줄었다. GSM8K의 5-shot 평가에서는 BF16 기준 **91.43%**, 압축판 **88.17%**로, 3.26%포인트 낮았다. 수학 문제 앞에 풀이 예시 다섯 개를 제공한 공급자 측정이며, 일반적인 업무 정확도나 CPU 속도 비교가 아니다.

또한 같은 체크포인트가 Zen CPU에서 동적 INT8 활성값을 사용하는 DA8W4 경로로도 실행될 수 있다고 카드가 설명한다. 파일명만 보고 실제 커널 경로까지 고정됐다고 생각하면 안 된다. 이름·가중치 저장 형식·실행 시 정밀도는 별개다.

**실무 시사점**

대상은 GPU 없이 기존 CPU 서버에서 언어모델을 연구·평가하려는 인프라 팀이다. 카드가 안내하는 버전을 고정하고, 실행 로그에서 실제 정밀도 경로를 먼저 확인하는 계획을 세우자. 같은 입력 길이·출력 상한·동시 사용자로 원본과 압축판의 업무 정확도, 첫 토큰 지연, 처리량, 최대 메모리를 비교한다.

완료 기준은 ‘파일이 작아졌다’가 아니라 실제 서비스 조건에서 품질 하락을 수용할 수 있고 지연·메모리 예산을 함께 만족하는지다. 특히 5.4GiB를 서버 전체 필요 메모리로 사용하지 말아야 한다. 캐시와 실행 버퍼를 포함한 값을 따로 측정해야 한다. 이번에는 문서와 공개 파일 기록만 검토했으며 설치·양자화·추론은 실행하지 않았다.

**한계 및 의문**

공개된 정확도 표는 한 벤치마크이며 처리량 개선을 입증하는 비교 표는 아니다. 카드의 평가 명령과 런타임 기본 경로 설명만으로 실제 평가가 어느 커널 경로였는지 완전히 확정하기 어려워, 재현 시 설정을 추가로 기록해야 한다. 버전이 다른 환경의 로딩·성능을 보장하지 않는다.

이번 발표는 압축 파일 공개다. 기존 Granite 모델의 능력을 이날 새로 학습한 결과로 소개하지 않았다. 카드와 초기 커밋은 Apache 2.0을 표기한다. 정확한 UTC 업로드 시각은 확보하지 못했으며, 초기 카드의 미완성 버전 표기와 현재 안내를 혼합하지 않았다.
