### 1. OmniSVG의 ONNX 배포: 새 모델이 아니라 로컬 실행 경로가 늘었다

- **출처**: Moonbox 공식 Hugging Face 모델 카드·업로드 기록 / 원 모델: OmniSVG 연구진
- **점수**: 7.4/10 — 편집 선정 점수
- **URL**: https://huggingface.co/moonbox-dev/OmniSVG1.1_4B-ONNX

**요약**

Moonbox가 기존 OmniSVG 1.1 4B의 ONNX 실행 패키지를 공개했다. 텍스트나 이미지를 확대해도 선이 유지되는 SVG 벡터 그래픽으로 바꾸는 모델을, 원래 PyTorch 경로 대신 ONNX Runtime의 CPU·CUDA 경로로 실행하도록 변환한 것이다. 11월 22일 공개 소식과 업로드 기록을 확인했으며, 새 모델을 학습한 발표는 아니다. 원 모델 카드의 갱신일은 2025-12-02로 표시되어 있다.

**맥락**

현재 변환 카드에는 fp16·int8·int4 폴더와 실행용 `pipeline.py`가 있다. 이름은 주된 정밀도를 뜻하며 모든 연산이 같은 비트 수라는 의미는 아니다. 특히 int4도 일부 계층은 8비트로 유지한다. 개발자 측정에서 RTX 3080 Laptop GPU로 8개 시퀀스·각 최대 1,536토큰을 생성할 때 fp16은 약 180초, int8·int4는 약 240초, 원 구현은 약 130초였다. 이 환경에서는 양자화가 속도를 높이지 않았다.

**실무 시사점**

대상은 벡터 생성 모델의 로컬 실행을 연구하는 팀이다. 우선 이용 조건과 출력 포맷을 확인하고, 별도 검토 환경에서 동일 입력·토큰 상한·후보 수를 고정한 비교 계획을 세우자. 아이콘뿐 아니라 얇은 선, 복잡한 곡선, 이미지 입력을 포함하고 생성 시간·메모리·실제 렌더 결과를 따로 기록하는 것이 좋다. 완료 기준은 파일 크기 감소 자체가 아니라 원하는 도형이 유지되고 대상 장치의 시간·메모리 예산을 만족하는지다.

모델 카드의 설치·실행 예시는 참고 자료로만 검토했으며 이번 작성에서는 다운로드·설치·추론을 실행하지 않았다. 새로운 런타임 경로를 확인한 것이지, 이식의 정확성을 독립 재현한 것은 아니다.

**한계 및 의문**

개발자의 6개 텍스트·2개 이미지 시험에서 각 빌드의 32개 후보가 모두 유효 판정을 받았다. 다만 유효성은 렌더가 비어 있지 않다는 조건이지 그림의 정확도나 편집 품질이 아니다. 작은 시험군의 결과를 전체 품질 보존으로 확대할 수 없다.

변환 패키지는 Apache 2.0 표기 외에 기반 Qwen의 연구용 조건을 함께 안내하며 비상업 용도로 명시한다. 원 모델의 라이선스 배지만 보고 이 패키지를 상업 배포 가능한 것으로 판단하지 않아야 한다. 업로드의 정확한 UTC 시각은 이번 접근에서 확보하지 못했고, 모델 카드도 계속 갱신되는 문서다.

### 2. Tether 0.4.0: 에이전트 기록을 회귀 테스트로 바꾼다

- **출처**: chizy7/tether 공식 GitHub 릴리스·버전 고정 문서
- **점수**: 7.6/10 — 편집 선정 점수
- **URL**: https://github.com/chizy7/tether/releases/tag/v0.4.0

**요약**

Tether 0.4.0이 **2026-11-22 05:04:50 UTC** GitHub 릴리스로 배포됐다. 이미 있는 에이전트의 모델·도구 호출을 기록하고 정책을 적용하는 실행 도구이며, 새 에이전트 모델이 아니다. 이번 버전은 기록된 작업 묶음을 `eval.toml`의 기대 조건과 대조하는 `tether eval`, 로컬 브라우저 기록 뷰어 등을 추가했다. 변경 이력에는 11월 21일로 적혀 있으므로 문서 날짜와 실제 릴리스 게시 시각을 구분했다.

**맥락**

기대 조건에는 완료 여부, 단계·비용 한도, 호출해야 하거나 호출하면 안 되는 도구, 기록에서 확인 가능한 파일 내용 등이 들어간다. 기록을 그대로 재생할 때는 저장된 모델 응답과 도구 결과를 돌려주므로 모델을 다시 부르지 않는다. 그러나 프롬프트나 모델을 바꿔 원래 요청과 달라지면 새 호출과 실제 도구 실행이 필요한 경로로 넘어갈 수 있다. 따라서 ‘평가 기능이 있다’와 ‘모든 비교가 무료다’는 같은 말이 아니다.

추가로 추적 형식을 v0으로 고정하고 이전 0.3.0 기록을 읽는 호환성 테스트를 둔다. 중요한 변화는 단순 로그 열람을 넘어, 어떤 작업에서 어느 조건이 어긋났는지를 반복 점검하는 인터페이스가 생겼다는 것이다.

**실무 시사점**

대상은 프롬프트·도구 정책·모델을 바꾸면서 기존 작업의 회귀를 확인하려는 개발팀이다. 먼저 승인된 비민감 기록으로 기대 결과와 금지 호출을 정의하고, 기록 재생만 하는 검사와 새 모델을 호출하는 검사를 분리하는 계획을 세우자. 새 호출을 허용하지 않는 검증에서는 모델·프롬프트 변경 옵션을 섞지 않고, 기록이 답할 수 없는 지점에서 무엇이 일어나는지 확인해야 한다.

완료 기준은 총 통과율 하나가 아니다. 실패 작업, 최초 분기 지점, 위반 조건, 새 호출 유무와 비용을 작업별로 설명할 수 있어야 한다. 파일에 관한 단언도 기록된 도구 결과로 확인한 것인지 실제 파일 시스템을 새로 조사한 것인지 구분하자. 이번 작성에서는 저장소 문서만 읽었으며 설치·예제·평가 명령이나 유료 모델 호출을 실행하지 않았다.

**한계 및 의문**

공식 예제는 20개 소형 작업이다. 스크립트 모델을 쓴 변경 프롬프트 예제에서는 3개가 실패하고, 문서의 실제 모델 실행 사례에서는 1개가 실패했다. 두 숫자는 서로 다른 실행 조건이며 일반적인 에이전트 신뢰도 측정값이 아니다. 문자열·호출·예산 단언을 통과해도 복잡한 결과의 의미적 정답성을 자동 보장하지 않는다.

원래 정책이 막아 실행하지 않은 도구의 결과는 기록에 없다. 이후 느슨한 정책으로 재생해도 그 행동의 결과를 과거 기록에서 알아낼 수 없다. 또한 도구는 단일 유지보수자의 pre-alpha 상태다. 기본 `process` 백엔드는 보안 격리 경계가 아니라고 README가 명시하며, 새 모델 호출을 가로챌 수 없는 프레임워크까지 모두 감쌀 수 있는 것도 아니다.
