### 1. Palette 3.0의 오늘 발표: 병렬 엣지 실행을 강조하되 SDK 배포일은 구분한다

- **출처**: SiMa.ai 공식 보도자료·개발자 커뮤니티·모델 브라우저
- **점수**: 8.0/10 *(편집 선정 점수이며 벤치마크 점수가 아님)*
- **URL**: https://sima.ai/press-release/industry-first-agentic-software-suite-palette-3-0/
- **원 게시자**: SiMa.ai
- **발견 경로**: 엣지 AI 최신 기사 검색 → 회사 보도자료 → 앞선 배포 공지·실제 제공 페이지 대조
- **보도자료 게시일**: 2026-11-17; 정확한 게시 시각 미표시
- **선행 배포일**: SDK는 2026-10-31 배포, 커뮤니티 공지는 2026-11-02
- **수정일**: 보도자료의 별도 수정일 미확인
- **확인일**: 2026-11-17
- **상태**: 새 공식 발표와 제공 상태 점검; 모든 기능의 당일 최초 출시로 보지 않음

**요약**

SiMa.ai가 Palette 3.0의 다중 모델 실행과 모델 브라우저를 공식 발표했다. Modalix 칩에서 언어·비전 모델과 별도 컨테이너의 작업을 함께 실행하는 구성을 강조한다. 회사는 speculative decoding으로 토큰 생성 처리량이 최대 **3.5배** 늘어난다고 주장한다. 다만 SDK 자체는 이미 10월 31일 배포됐으므로, 오늘의 보도자료 날짜와 소프트웨어 최초 배포일을 구분해야 한다.

**맥락**

Speculative decoding은 여러 후보 토큰을 먼저 만들고 목표 모델이 검증하는 방식이다. 생성 단계의 개선과 카메라 입력·전처리·첫 응답까지 포함한 전체 지연은 다르다. 엣지 시스템에서는 여러 모델이 자원을 나눠 쓰는 조건도 중요하다는 것이 편집부의 해석이다.

공식 보도자료가 연결한 모델 브라우저를 열면 현재 **비공식 스테이징 빌드**라는 안내가 표시된다. 페이지가 존재한다는 사실만으로 성능 표 전체와 다운로드 흐름의 정식 제공을 확인했다고 할 수 없다. 이번에 완전한 모델별 비교표를 읽어 독립 검증하지는 못했다.

**실무 시사점**

Modalix를 쓰는 비전·로봇 팀은 기존 앱 복사본에서 감지 모델과 언어 모델을 동시에 실행하는 조건을 시험하자. 평균 처리량 외에 중요 작업의 p95/p99 지연, 메모리, 전력과 입력 누락을 기록한다. 완료 기준은 생성 속도가 아니라 중요한 센서 작업의 마감 시간을 유지하면서 전체 앱의 품질·비용 기준을 만족하는 것이다.

업그레이드 절차도 별개다. 공식 커뮤니티는 Neat 0.6.0에 Platform 3.0.0이 필요하며 네이티브 앱 재빌드를 요구한다. 2.1.3 보드를 일반 업데이트만으로 전환할 수 없다고 안내한다. 버전 조합과 복구 방법을 확인한 뒤 검증해야 한다. 이는 편집부의 제안이며 이번에 수행한 실험이 아니다.

**한계 및 의문**

3.5배는 공급사의 상한 표현이다. 다른 모델·입력 길이·동시 부하에서 같은 배수를 기대할 근거는 없다. 장치 전체의 소비전력 개선으로 확대하지 않는다. 공개 코드 링크가 있어도 SDK·펌웨어·모델 자산 전체의 라이선스가 같거나 실행 비용이 없다고 가정하지 않는다. 스테이징 브라우저의 정식 제공 시점도 확인되지 않았다.

선별 배치 계획을 누구나 즉시 구매 가능한 상태나 인도 완료 수량으로 바꾸지 않았다. ‘사람 수준의 손재주’ 같은 홍보 표현도 객관적으로 달성한 성과로 인용하지 않는다.

### 3. Langfuse v4.82.0: 평가 모델이 요청 제한에 걸리면 같은 연결의 해당 모델을 잠시 쉰다

- **출처**: Langfuse GitHub 공식 릴리스·PR·버전 고정 소스
- **점수**: 7.9/10 *(편집 선정 점수이며 벤치마크 점수가 아님)*
- **URL**: https://github.com/langfuse/langfuse/releases/tag/v4.82.0
- **원 게시자**: Langfuse 프로젝트
- **발견 경로**: 공개 ML 도구 최신 릴리스 검색 → GitHub 릴리스 API → PR #20289 → v4.82.0 구현 대조
- **릴리스 공개**: 2026-11-17 14:28:42 UTC / 15:28:42 CET
- **해당 PR 병합**: 2026-11-16 18:00:38 UTC; 릴리스 공개 시각과 구분
- **수정일**: 릴리스의 별도 수정 이력은 검증하지 않음
- **확인일**: 2026-11-17
- **상태**: 공개 릴리스에 코드 포함 확인; 모든 호스팅 환경에 동시 적용됐다는 뜻은 아님

**요약**

Langfuse v4.82.0은 LLM 평가 요청이 공급자의 속도 제한 응답인 HTTP 429를 받았을 때의 처리를 바꿨다. 호출 내부의 즉시 재시도 대신, 큐의 재예약과 연결·모델 단위 휴지 시간을 사용한다. 같은 연결의 다른 모델까지 일괄 중지하지는 않는다. 이는 평가 점수를 높이는 변경이 아니라, 평가 작업이 제한된 요청 자원을 사용하는 방식을 조정한 수정이다.

**맥락**

기존 PR 설명은 각 평가 작업이 제한된 연결을 반복 호출하고 내부 재시도까지 추가하던 문제를 지적한다. v4.82.0 소스에서 평가 호출의 `maxRetries: 0`을 확인했다. 냉각 시간 키는 연결 식별자와 모델 이름을 함께 사용한다.

구현의 기본 휴지 시간은 **60초**, 최소·최대는 **5–300초**다. Redis에서 남은 시간을 확인하면 공급자를 다시 호출하지 않고 재시도 가능한 오류를 반환한다. 큐 재예약과 호출 내부 재시도는 같은 기능이 아니라는 점이 핵심이다.

**실무 시사점**

LLM 기반 평가를 운영하는 팀은 실제 공급자를 호출하지 않는 모의 429 시험을 먼저 만들자. 같은 모델의 후속 호출은 잠시 건너뛰고 다른 모델의 작업은 유지되는지, 재예약 횟수와 작업 지연이 어떻게 바뀌는지 확인한다. 정상 응답, 요청 크기 초과, 결제 한도 오류를 구분해서 시험한다.

완료 기준은 ‘429가 사라짐’이 아니다. 중복 호출을 줄이면서 누락 작업과 재시도 소진을 관측할 수 있고, 정상 작업의 지연이 사전 기준 안에 있어야 한다. 이는 편집 제안이다. 이번에는 소스와 테스트 변경만 읽었으며 평가 실행이나 유료 모델 호출은 하지 않았다.

**한계 및 의문**

이 변경은 전역 동시 실행 수 제한이 아니다. Redis가 준비되지 않았거나 조회·기록이 실패하면 호출을 진행하는 fail-open 동작이 남는다. 구현은 Redis 대기에 **1초** 기한을 두지만, 그것만으로 요청 폭주를 완전히 막지는 않는다.

PR은 실험 기능의 항목별 LLM 오류 경로가 이번 범위 밖임을 명시한다. 모든 평가·실험·게이트웨이에 같은 정책이 적용된다고 일반화하지 않는다. 공개 테스트가 있다는 사실과 이번 환경에서 테스트를 재실행했다는 사실도 구분한다.
