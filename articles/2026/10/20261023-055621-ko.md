# 학습 루프는 직접, GPU 운영은 서버리스로: SageMaker가 후학습의 경계를 낮췄다

## 트렌드 분석

파운데이션 모델 커스터마이징은 그동안 두 극단 사이에 있었다. 완전 관리형 fine-tuning은 GPU 운영이 쉽지만 손실함수와 학습 순서를 바꾸기 어렵고, 직접 클러스터를 운영하면 알고리즘 자유도는 높지만 분산 실행·checkpoint·장애 복구를 팀이 책임져야 했다. AWS가 일반 제공을 발표한 SageMaker AI training session APIs는 이 경계를 학습 작업 단위로 옮긴다. 사용자는 Python에서 sampling, reward 계산, gradient update의 순서를 직접 쓰고, SageMaker는 모델을 GPU에 올린 채 분산 실행과 복구를 맡는다.

특히 agent 후학습에서는 응답 생성, 외부 도구 실행, verifier 채점, weight update가 서로 다른 환경에서 반복된다. 새 API는 GPU가 필요한 `sample`, `forward_backward`, `optim_step` 등을 stateful session 호출로 제공하고, reward·환경·도구 실행은 사용자의 로컬 또는 자체 인프라에 남긴다. 알고리즘을 서비스에 넘기는 대신 compute만 추상화한 셈이다.

하지만 ‘서버리스’가 무제한·무관리·저비용을 뜻하지는 않는다. prefill, 생성 sample, training token이 각각 과금되고 활성 session은 동시 세션 quota를 점유한다. 지원 모델과 리전도 제한적이며, 발표 글과 현재 공식 문서의 지원 모델 목록이 완전히 일치하지 않는다. 따라서 도입 판단은 편의성보다 반복 가능한 품질·총토큰 비용·데이터 경계·종료 처리까지 포함해 내려야 한다.

**요약**

AWS는 SageMaker AI serverless model customization의 training session APIs를 일반 제공했다. 개발자는 로컬 Python 프로세스에서 학습 루프와 reward function을 작성하고, SageMaker가 GPU 할당, 모델·LoRA adapter 로딩, 분산 실행, gradient synchronization, 장애 복구와 checkpoint 저장을 처리한다. 사전 정의된 recipe만 고르는 관리형 fine-tuning보다 알고리즘 제어 범위가 넓고, instance type과 클러스터를 직접 고르는 Training Jobs·HyperPod보다 인프라 책임이 적다.

API는 대략 세 계층으로 나뉜다. `ServiceClient`가 IAM role, S3 출력 경로, KMS·VPC 설정과 session 생성을 맡고, `TrainingClient`가 forward/backward·optimizer·checkpoint 작업을, `SamplingClient`가 생성과 log-probability 계산을 담당한다. 모델은 session 동안 GPU에 유지되므로 사용자는 여러 호출을 조합해 SFT, preference optimization, GRPO·PPO 계열 RL 또는 custom objective를 구현할 수 있다.

**맥락**

agent용 multi-turn RL은 한 번의 정답 생성보다 복잡하다. 현재 policy로 여러 trajectory를 만들고, agent가 도구 또는 simulator와 상호작용한 결과를 verifier로 채점한 뒤 reward를 gradient update로 반영해야 한다. 새 구조에서는 GPU-bound sampling과 update만 관리형 session에서 실행하고, 환경·reward·sandbox·loop control은 사용자가 소유한다. reward 계산 동안에는 GPU 작업 토큰이 발생하지 않는다고 AWS는 설명한다.

공개 Code RL recipe는 GPT-OSS 20B에 rank 32 LoRA adapter를 적용했다. 50 step 동안 step당 128개 문제와 문제당 8개 응답, 2 turn, staleness bound `k=3` 조건으로 학습했고, training reward가 0.46에서 0.60으로, 200개 held-out 문제 정확도가 40.0%에서 50.5%로 올랐다고 보고했다. 이는 단일 공개 recipe의 결과이며 서비스 전체의 성능 보장이나 다른 데이터셋의 기대 향상폭이 아니다.

**실무 시사점**

- **대상:** 표준 fine-tuning recipe로 표현하기 어려운 custom loss·reward·multi-turn agent 학습을 원하지만 GPU 클러스터 운영은 피하려는 ML 팀
- **방법:** 먼저 동일 데이터와 seed로 기존 관리형 recipe를 baseline으로 실행한다. training session에서는 reward 함수, rollout 수, 생성 길이, update 횟수와 checkpoint 주기를 고정하고 prefill·sample·train 토큰을 각각 기록한다. reward 코드는 모델 session과 분리해 unit test하고, holdout 평가는 학습 verifier와 다른 경로로 수행한다.
- **완료 기준:** 최소 3개 seed의 holdout 품질 향상이 사전 기준을 넘고, 실패 재시작 후 checkpoint 결과가 일치하며, 총비용과 운영시간이 기존 Training Job 또는 자체 클러스터 baseline보다 목표 범위 안에 들어올 때만 production 후보로 승격한다.

보안 면에서는 IAM execution role, 동일 리전 S3, 선택적 KMS key와 VPC 설정을 사용할 수 있다. session은 자동으로 무해한 추상 객체가 되는 것이 아니므로 최소 권한 role, 데이터 bucket 정책, 외부 reward service의 egress, checkpoint 보존 정책을 별도로 검토해야 한다.

**한계 및 의문**

과금은 단일 ‘학습 토큰’이 아니라 prefill, sample, train 세 차원으로 나뉜다. reward 계산이 길 때 GPU wall-clock 과금이 멈추는 장점은 있지만, 긴 context·많은 rollout·여러 backward pass는 토큰 비용을 빠르게 키울 수 있다. AWS 공개 발표에는 절대 단가 비교나 자체 클러스터 대비 총비용 실험이 없어 ‘더 저렴하다’고 일반화할 수 없다. 활성 session은 동시 세션 quota를 점유하므로 예외 처리에서 반드시 session을 중지해야 한다.

지원 범위에도 확인이 필요하다. 발표 글은 `gpt-oss-20b`, `gemma-4-31B-it`, `Qwen3.6-27B`, `Qwen3.8-27B`를 열거하지만, 2026-10-23 확인한 공식 지원 표에는 GPT-OSS-20B, Gemma-4-31B-it, Qwen-3.6-27B만 보인다. 리전은 모델별로 `us-east-1`, `us-west-2`, `ap-south-1` 일부 조합에 한정된다. 실제 사용 전 `list_base_models()`로 계정·리전에서 보이는 모델을 확인해야 하며, 발표 목록만 하드코딩하면 안 된다.

공개 예제의 정확도 상승은 200개 held-out 문제라는 작은 평가에서 얻은 공급사 결과다. base model의 여러 seed, 독립 재현, contamination 검사, 비용, 안전 평가가 제시되지 않았다. 외부 reward model이나 tool sandbox를 잘못 설계하면 관리형 GPU 여부와 무관하게 reward hacking·데이터 유출·잘못된 최적화가 발생할 수 있다.
